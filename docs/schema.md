# Schema and table grain

All data is generated by `scripts/build.py`, with no external source. ISO dates are local calendar dates; no timezone conversion. Quantities are kg except order/delivery quantity, which is units of finished product. Do not compare or add those quantities together.

| Table | One row represents | Primary key | Foreign keys / important columns |
|---|---|---|---|
| machine | Machine | machine_id | machine_name |
| product | Finished product | product_id | product_name |
| production | Scheduled run on one machine for one product | run_id | run_date, machine_id, product_id; planned_minutes, input_qty kg, waste_qty kg, unit |
| downtime | Non-overlapping interval within a run | event_id | run_id; start_minute/end_minute offsets, reason; enriched run_date/machine_id/product_id; derived downtime_minutes |
| orders | Customer order for one product | order_id | product_id; order_date, due_date, quantity in finished units |
| deliveries | One full shipment completing one order (MVP restriction) | delivery_id | order_id; delivered_date, quantity in finished units |
| delivery_order | Order plus completion/overdue state as of snapshot | order_id | product_id, order_date, due_date, quantity; delivered_date nullable; three 0/1 flags |
| dim_date | October calendar day including non-production day 31 | date | ISO date |
| settings | Snapshot configuration (exactly one row) | none | as_of_date |

Source production has an exact repeated ID/row. `SELECT DISTINCT` removes exact repeats; quality checks reject remaining conflicting IDs. Other clean grains are tested for uniqueness. Raw records are preserved in CSV; quarantine is an issue log with source and record ID, and rejected rows can be retrieved from raw tables by that ID.

Do not join production to downtime and then sum production quantities: every run has two events, so the join doubles planned minutes, input and waste. Aggregate facts independently before joining summaries. `sql/03_metrics.sql` demonstrates this. In Power BI use shared dimension filtering with independent measures. No fact-to-fact relationship is needed.

The order mart is intentionally derived at order grain for rate counts. Load that mart into Power BI; leave raw orders/deliveries out of the report model. Dates on delivery pages represent **orders due in the selected period**, measured as of the fixed snapshot. This differs from a delivery-date throughput report.
